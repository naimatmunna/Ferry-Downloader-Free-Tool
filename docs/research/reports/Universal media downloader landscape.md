# Build the downloader around permission, not extraction

A compliance-first universal downloader can be built in November 2026 on a settled engine stack — **yt-dlp 2026.11.23** for extraction, an **LGPL build of FFmpeg 9.x** for remuxing, **gallery-dl** for image galleries and, optionally, **Streamlink** for live recording, each run as a sandboxed subprocess — but the binding constraint is permission, not technology. yt-dlp alone reaches **about 1,000 distinct platforms**, yet of the 53 platforms whose terms were reviewed for this research only **11 offer a sanctioned viewer download and 11 more permit downloading by licence**, while **21 — YouTube, TikTok, Instagram, X, Reddit and Twitch among them — are technically extractable but closed to third-party tools**, and the remainder allow only owner exports or are protected. YouTube is the crux: its Terms, its API Services Terms (§16.3) and its Developer Policies (III.E.1, III.I.14) withhold any download right, courts in Connecticut (2022) and Hamburg (2024) treated solving its rolling cipher — the exact job of the JavaScript runtime yt-dlp now requires — as circumventing an effective protection measure, and IFPI asked the European Commission in September 2026 to list yt-dlp itself as a piracy service. The market leaves a clear opening: ad-funded rippers have been sued, blocked or shut down in at least eight jurisdictions, paid desktop tools break with each YouTube change and strand paid licences, and the cleanest free web tool, Cobalt, lost YouTube on its main instance and has been dormant since April 2026. On phones, the browser's own download manager, fed by a same-origin `Content-Disposition: attachment` response with a strong ETag, beats every PWA API; Android's Web Share Target is the one PWA feature worth shipping, and iOS Home Screen web apps currently break downloads outright. The architecture that follows is a hostname-keyed permission registry with YouTube extraction, cookies, impersonation, PO tokens and DRM handling off by design, connectors that prefer official APIs and owner exports, and a product that competes on honesty, privacy and a clean share-to-save flow rather than on site counts.

## yt-dlp and FFmpeg anchor the stack while Cobalt and aria2 fail review

yt-dlp is the only extraction engine with the breadth, release velocity and security response a production service needs. **Version 2026.11.23** shipped on 23 November 2026, about the tenth stable release since February, from a project with 210,249 GitHub stars, roughly 2,100 open issues and 701 open pull requests ([yt-dlp releases](https://github.com/yt-dlp/yt-dlp/releases); [yt-dlp repository](https://github.com/yt-dlp/yt-dlp)). It is released under the **Unlicense** and now requires **Python 3.11 or newer**, having dropped 3.10 at its end of life in release 2026.10.26 ([yt-dlp releases](https://github.com/yt-dlp/yt-dlp/releases)). Churn is constant: 2026.11.23 alone added an `ios_producer` YouTube client, temporarily removed `web` from the default clients and made `tv` the default player-JS variant ([yt-dlp 2026.11.23](https://github.com/yt-dlp/yt-dlp/releases/tag/2026.11.23)), so operators should budget for upgrades every one to four weeks. Its `default` dependency extra pins **yt-dlp-ejs 0.8.0** (Unlicense AND MIT AND ISC) and pulls in mutagen (GPLv2+) and certifi (MPL-2.0), licences that matter only when container images are distributed ([local yt-dlp 2026.11.23 metadata](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp-2026.11.23.dist-info/METADATA); [PyPI: yt-dlp-ejs](https://pypi.org/pypi/yt-dlp-ejs/json)).

The JavaScript-runtime requirement is the dependency that changed most. Since release 2025.11.12, full YouTube support needs an external runtime to execute the yt-dlp-ejs solver scripts against YouTube's player challenges; without one, yt-dlp drops the `web` and `tv_samsung` clients, falls back to `visionos` and offers fewer formats ([yt-dlp issue #15012](https://github.com/yt-dlp/yt-dlp/issues/15012); [yt-dlp EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). Four runtimes qualify. **Deno 2.3.0+** is the only one enabled by default and the only one documented as running without filesystem or network access; yt-dlp launches it with no `--allow-*` grants at all ([local yt-dlp deno.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/extractor/youtube/jsc/_builtin/deno.py)). **Node 22.0.0+** is supported but off by default; the 2025 announcement cited Node 20, but the 2026 code constant is 22 ([local yt-dlp _jsruntime.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/utils/_jsruntime.py)). QuickJS (2023-12-09 or later, or any QuickJS-NG release) works but can take minutes per solve on older builds, and Bun 1.2.11–1.3.14 is deprecated ([yt-dlp EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). The Node 24 that a Node.js worker already ships can be used by passing `--no-js-runtimes --js-runtimes node:<path>` — the first flag stops a stray Deno from winning on priority — after which yt-dlp runs `node --permission -` with the solver on stdin; the maintainers nonetheless still describe Node and Bun as insecure compared with Deno ([local yt-dlp node.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/extractor/youtube/jsc/_builtin/node.py); [local yt-dlp README](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp-2026.11.23.dist-info/METADATA)). The more consequential point is what the runtime does: it solves the signature and n-parameter challenge that courts have treated as an access control, so choosing a runtime is really choosing a YouTube policy.

Hardening matters because nearly all of yt-dlp's vulnerabilities live in optional features. GitHub lists **13 advisories**, ten within the last three years and **six published in 2026**: a `--netrc-cmd` injection (CVE-2026-26331), four on 9 June — including **CVE-2026-50574**, scored 9.6 by NVD, in which crafted HLS or DASH manifests inject options into aria2c — and an internet-shortcut injection (CVE-2026-55404), all fixed by **2026.07.04** ([yt-dlp security advisories](https://api.github.com/repos/yt-dlp/yt-dlp/security-advisories?per_page=100)). Two of them bypass earlier fixes (CVE-2024-22423 then CVE-2025-54072 for Windows `--exec` escaping; CVE-2024-38519 then CVE-2026-50023 for unsafe file extensions), and release 2026.10.21 warned that old executables are exposed to man-in-the-middle attacks through a certifi flaw and told users to avoid the self-updater ([yt-dlp 2026.10.21](https://api.github.com/repos/yt-dlp/yt-dlp/releases/tags/2026.10.21)). A server should pin a current release; never pass `--exec`, `--netrc-cmd`, `--write-*link`, `--cookies-from-browser` or the `allow-unsafe-*` compatibility options; force the native downloader; and run with `--ignore-config` and `--no-plugin-dirs` (or `YTDLP_NO_PLUGINS=1`), because plugins found on any `sys.path` entry are imported automatically and can override built-in extractors ([local yt-dlp --help](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Scripts/yt-dlp.exe); [local yt-dlp plugins.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/plugins.py)). Restricting extractors with `--ies` to an allowlist that excludes `generic` removes the vector named in two advisories, and `--xff never` disables the default behaviour of forging X-Forwarded-For headers wherever an extractor deems that useful for dodging geo-blocks. One trap deserves emphasis: **`--max-filesize` aborts only when the server announces a length, and the HLS/DASH fragment downloaders never check it**, so the worker itself must kill the process once `progress.downloaded_bytes` passes the cap ([local yt-dlp http.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/downloader/http.py)).

DRM handling is already conservative and should stay that way. Extractors mark formats with `has_drm`; yt-dlp removes protected formats before selection, raises a DRM-protected error when nothing playable remains, and retains them only under a hidden developer flag, `--allow-unplayable-formats`, which still never decrypts ([local yt-dlp YoutubeDL.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/YoutubeDL.py)). A true `_has_drm` in a metadata preview should be a hard compliance stop, but its absence is not proof of clean media, because the HLS detector matches FairPlay, PlayReady and Adobe Access key formats without listing Widevine ([local yt-dlp hls.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/downloader/hls.py)). Size metadata is similarly uneven: an exact `filesize` is mostly present only for progressive HTTP formats, and yt-dlp stopped estimating `filesize_approx` for manifest formats in 2023 because the estimates were wildly inaccurate, so any pre-download size shown to users must be labelled as an estimate ([local yt-dlp README](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp-2026.11.23.dist-info/METADATA)).

FFmpeg is mandatory for merging streams and extracting audio. The current release is **FFmpeg 9.1 "Gauss" (20 November 2026)**, with point releases still shipping on branches back to 4.4 ([FFmpeg download page](https://ffmpeg.org/download.html)). Its licence is a build decision: FFmpeg is LGPL-2.1+ by default; `--enable-gpl` (required for libx264, libx265, libxvid and several filters) makes the whole binary GPL; BtbN's gpl builds also set `--enable-version3` and are therefore GPLv3+; and `--enable-nonfree` (for fdk-aac) produces a binary that cannot be redistributed ([FFmpeg legal](https://ffmpeg.org/legal.html); [FFmpeg LICENSE.md](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/LICENSE.md); [BtbN FFmpeg-Builds](https://github.com/BtbN/FFmpeg-Builds)). Because GPL and LGPL duties attach to distribution and FFmpeg is not AGPL, running even a GPL build as a separate subprocess in a hosted service imposes no source obligation on the Node.js code, whereas shipping a container image to customers does; a downloader that mostly remuxes with `-c copy` and encodes royalty-free audio needs only an LGPL build. Local mux tests on synthetic signals confirmed the container rules the interface must enforce: WebM accepts only VP8, VP9 or AV1 with Vorbis or Opus; MOV rejects VP9, AV1 and Opus; the M4A muxer rejects Opus; and MP4 accepts Opus, VP9, AV1, FLAC and MP3 ([local FFmpeg 9.0.2 tests](file:///C:/Users/weeam%20server/AppData/Local/Microsoft/WinGet/Packages/BtbN.FFmpeg.GPL.9.0_Microsoft.Winget.Source_8wekyb3d8bbwe/ffmpeg-n9.0.2-39-g7adfbe40dc-win64-gpl-9.0/bin/ffmpeg.exe)). Security is the other reason to sandbox it. The project's security page lists eight CVEs fixed in 9.0, while an NVD keyword search returned 186 FFmpeg CVEs published between late July and late November 2026 — including a CVSS 9.8 heap overflow in the RIST protocol (CVE-2026-75143) and an 8.1 out-of-bounds read in the DASH demuxer (CVE-2026-75146), both fixed by commit with no release named — and the security page lags NVD ([FFmpeg security](https://ffmpeg.org/security.html); [NVD FFmpeg query](https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch=FFmpeg&pubStartDate=2026-07-27T00:00:00.000&pubEndDate=2026-11-24T00:00:00.000)). Run it with `-protocol_whitelist file`, `-nostdin`, `-xerror`, `-max_alloc`, `-fs` and `-timelimit`, with no network access, and let yt-dlp's native downloader fetch segments so FFmpeg touches only local files; the HLS demuxer's default list of allowed segment extensions even includes `html` ([local FFmpeg 9.0.2 options](file:///C:/Users/weeam%20server/AppData/Local/Microsoft/WinGet/Packages/BtbN.FFmpeg.GPL.9.0_Microsoft.Winget.Source_8wekyb3d8bbwe/ffmpeg-n9.0.2-39-g7adfbe40dc-win64-gpl-9.0/bin/ffmpeg.exe)).

gallery-dl and Streamlink fill narrower gaps. gallery-dl (GPL-2.0-only; **v1.32.21** of 21 November 2026; eight releases in eight weeks; primary development now on Codeberg) is the strongest open engine for carousels and multi-image posts, and its `-j` message protocol of directory, file-URL and queue messages maps neatly onto a picker interface ([gallery-dl releases](https://api.github.com/repos/mikf/gallery-dl/releases?per_page=8); [gallery-dl README](https://raw.githubusercontent.com/mikf/gallery-dl/master/README.rst); [gallery-dl message.py](https://raw.githubusercontent.com/mikf/gallery-dl/master/gallery_dl/extractor/message.py)). It has no GitHub security advisories, but its roughly 358 site rows are dominated by image boards and adult sites — its own list warns that any listed site may be NSFW — and its mainstream extractors (Instagram, X, Reddit, Tumblr, pixiv) rely on cookies or OAuth, so it belongs behind a strict allowlist ([gallery-dl supported sites](https://github.com/mikf/gallery-dl/blob/master/docs/supportedsites.md); [gallery-dl advisories](https://api.github.com/repos/mikf/gallery-dl/security-advisories?per_page=50)). Streamlink (BSD-2-Clause; **8.6.3** of 29 October 2026; 132 site plugins) is the best open engine for recording live HLS and DASH streams, but its YouTube plugin is live-only, three 2026 advisories allowing local file reads were fully fixed only in 8.6.2, and its Twitch and Kick plugins depend on browser-obtained integrity tokens and JavaScript-challenge solving that a compliance-first product should disable ([Streamlink plugins](https://streamlink.github.io/plugins.html); [Streamlink advisories](https://api.github.com/repos/streamlink/streamlink/security-advisories?per_page=50)). For a small allowlist, yt-dlp's own live support can make Streamlink unnecessary at launch.

Cobalt, the best-known open web downloader with 47,054 GitHub stars, fails as an embedded engine on four counts. Its API is AGPL-3.0, its web frontend is CC-BY-NC-SA-4.0 (non-commercial) with unlicensed branding, and the hosted `api.cobalt.tools` is off-limits to other projects without permission ([cobalt web README](https://raw.githubusercontent.com/imputnet/cobalt/main/web/README.md); [cobalt API docs](https://raw.githubusercontent.com/imputnet/cobalt/main/docs/api.md)). The repository has been **dormant since 6 April 2026** (v11.7), with an open request to archive it filed on 17 November 2026 and YouTube pull requests left unmerged ([cobalt commits](https://api.github.com/repos/imputnet/cobalt/commits?per_page=12); [cobalt issue search](https://api.github.com/search/issues?q=repo:imputnet/cobalt+youtube+created:%3E2026-05-01&sort=created&order=desc&per_page=20)). Its YouTube path depends on youtubei.js plus an optional proof-of-origin session generator and an optional random-IPv6-per-download mode, both evasion features ([cobalt environment variables](https://raw.githubusercontent.com/imputnet/cobalt/main/docs/api-env-variables.md)). And it covers only 21 services ([cobalt API README](https://raw.githubusercontent.com/imputnet/cobalt/main/api/README.md)). Its response model — tunnel, redirect and picker responses, short-lived tunnel IDs and no content caching — is still worth copying. The older alternatives are stale: you-get's last release was January 2025 and lux's May 2024 (45 sites, no proxy flag), and aria2 has not released since November 2023 while carrying three unpatched 2026 CVEs, one in TLS certificate validation ([you-get releases](https://api.github.com/repos/soimort/you-get/releases?per_page=4); [lux README](https://raw.githubusercontent.com/iawia002/lux/master/README.md); [NVD aria2 query](https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch=aria2)). The popular 2025–26 newcomers are front-ends to yt-dlp and FFmpeg rather than new engines, and the largest, omniget, advertises access to logged-in accounts and purchased courses ([GitHub search: new downloaders](https://api.github.com/search/repositories?q=downloader+in:name,description,topics+created:%3E2025-01-01+stars:%3E800&sort=stars&order=desc&per_page=30)). N_m3u8DL-RE, which decrypts DASH, HLS and MSS streams when given keys, belongs on a prohibited list together with curl_cffi impersonation — which 21 yt-dlp extractor modules use automatically whenever it is installed — PO-token provider plugins, the hidden `--allow-unplayable-formats` flag and YouTube's ad-skipping extractor argument ([N_m3u8DL-RE README](https://raw.githubusercontent.com/nilaoda/N_m3u8DL-RE/main/README.md); [local yt-dlp common.py](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/extractor/common.py)).

## About 1,000 platforms are reachable, but only 22 of 53 reviewed permit downloads

Raw site counts overstate real coverage. yt-dlp's supported-sites list has **1,731 entries, 136 of them (7.9%) flagged as currently broken** ([yt-dlp supportedsites.md](https://github.com/yt-dlp/yt-dlp/blob/master/supportedsites.md)). Offline introspection of the installed 2026.11.23 code collapses those entries into 1,362 name families (1,250 with a working extractor) and 922 source modules (831 working), and finds 1,131 distinct registrable domains among real test URLs, 1,028 of them from working extractors; about 80 extractors are adult-flagged and 112 name prefixes are broken outright ([local yt-dlp extractor registry](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Lib/site-packages/yt_dlp/extractor/__init__.py)). The defensible estimate is **about 1,000 ± 100 distinct platforms, with a usable working set of roughly 800–900**, so an honest public claim is "850-plus working integrations", not "1,700-plus sites". gallery-dl adds about 358 site and instance rows across 31 instance families, only about 40 of them mainstream platforms, and Streamlink 132 site plugins ([gallery-dl supported sites](https://github.com/mikf/gallery-dl/blob/master/docs/supportedsites.md); [Streamlink plugin directory](https://github.com/streamlink/streamlink/tree/master/src/streamlink/plugins)). A curated catalog of 214 distinct platforms assembled for this research found **178–179 with at least one working engine path**; the rest are DRM services, policy refusals, dead services (Trovo ended live streaming on 30 June 2026 and Gfycat closed in 2023), fully broken extractors (Kuwo, Teachable) or platforms no engine supports, including Threads, Kuaishou, Coursera, edX, Skillshare, GIPHY, Pixabay, Openverse and MEGA ([Streams Charts](https://streamscharts.com/news/trovo-shut-down); [TechCrunch](https://techcrunch.com/2023/07/05/gfycat-shuts-down-on-september-1)).

The *working* flag is no health signal for the platforms users care about most. Reddit has an open issue, filed 31 October 2026, in which requests return HTTP 403 and then an IP-level block, with contributors saying cookies plus Chrome impersonation are now required ([yt-dlp #17965](https://github.com/yt-dlp/yt-dlp/issues/17965)); Facebook's new React login wall broke parsing until 2026.11.23 improved the error messages ([yt-dlp #18016](https://github.com/yt-dlp/yt-dlp/issues/18016)); Instagram stories failed even with valid cookies in autumn 2026, and `instagram:user` is flagged broken ([yt-dlp #17755](https://github.com/yt-dlp/yt-dlp/issues/17755)); X invalidates exported cookies ([yt-dlp #17950](https://github.com/yt-dlp/yt-dlp/issues/17950)); and TikTok's August 2026 breakage was fixed in 2026.08.19 for setups with curl_cffi impersonation available ([downstream fix](https://github.com/DaH4uk/tg-video-downloader/pull/22)). YouTube requires PO tokens for most clients, risks 403 errors and account or IP blocks without them, and serves DRM-protected tv-client formats to requests without cookies ([yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)). The mainstream social and video platforms therefore now work reliably only with the cookie, impersonation and attestation tooling a compliance-first product must refuse — and, as the next sections show, they are also the platforms whose terms close the door, so technical fragility and legal restriction point the same way.

A registry has to do more than match hostnames. Extractor patterns are strict: Imgur accepts only `imgur.com` and `i.imgur.com`, Bilibili's main extractor rejects `m.bilibili.com`, OK.ru rejects `m.ok.ru`, the JioHotstar extractor ignores `jiohotstar.com`, and ITV matches only legacy `/hub/` paths. Most shorteners (pin.it, redd.it, fb.watch, b23.tv, on.soundcloud.com) match nothing and work only because the generic extractor follows redirects — which an allowlist that drops `generic` will not do — so the service must resolve redirects itself before deciding capability ([yt-dlp generic.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/generic.py)). Federated platforms cannot be enumerated: the PeerTube extractor hard-codes about 1,000 instance hosts, and yt-dlp has no Mastodon extractor at all, so path or API probes are needed. yt-dlp also ships ready-made refusal lists that make a good deny-list seed: a hidden DRM extractor refuses Disney+, Prime Video, Hulu, Peacock, Paramount+, Crunchyroll, open.spotify.com, Deezer, Apple TV, `play.hbomax.com`, Channel 4 and 5, Viki, ZEE5 and about 25 more, and a liability extractor refuses suno.com and udio.com. Netflix, Apple Music, TIDAL and `max.com` are absent and must be added by hand ([yt-dlp unsupported.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/unsupported.py)).

The five download-permission categories were applied to 53 platforms — 18 social services and 35 video, audio, education and open-content services — by asking what the most permissive route is that a compliant third-party tool could rely on: (1) the platform itself offers viewers a download; (2) the only authorized file route is the account owner's export of their own content; (3) a licence or the terms permit downloading public media; (4) the media is technically retrievable but the terms grant viewers or tools no download right; (5) the content is DRM-protected, app-bound or governed by terms that cannot be verified. The two research tracks applied category 1 slightly differently — creator-gated in-app buttons on TikTok, Instagram Reels and X landed in category 4 because only the first-party app may use them, while creator-gated flags on Vimeo, PeerTube and SoundCloud landed in category 1 because the platform itself serves the file — and the distinction that reconciles them for engineering is whether the permission is **machine-readable by a third party**. PeerTube's `downloadEnabled`, Jamendo's `audiodownload_allowed`, the Internet Archive's `licenseurl` and `access-restricted-item`, Vimeo's API `download` links, RSS `<enclosure>` elements, Wikimedia's per-file licences and Flickr's licence IDs can all be checked before a fetch ([PeerTube VideoDetails](https://docs.joinpeertube.org/api-rest-reference/api/models/videodetails.html); [Jamendo tracks/file](https://developer.jamendo.com/v3.0/tracks/file); [Internet Archive metadata schema](https://archive.org/developers/metadata-schema/index.html); [Vimeo API download links](https://help.vimeo.com/hc/en-us/articles/12427806914577-Get-video-file-and-download-links-from-the-API); [RSS 2.0 specification](https://www.rssboard.org/rss-specification)). By contrast, TikTok's and Instagram's flags have no official API exposure, X documents `allow_download_status` only as write-side media metadata, SoundCloud's API terms forbid third-party file saving even for tracks the uploader made downloadable, and Telegram's `noforwards` — the one creator flag readable through an official API — is a prohibition rather than a grant ([X API: media metadata](https://docs.x.com/x-api/media/create-media-metadata); [SoundCloud API Terms](https://developers.soundcloud.com/docs/api/terms-of-use); [Telegram content protection](https://core.telegram.org/api/content-protection)).

The distribution is stark. Only **22 of the 53 reviewed platforms** sit in categories 1 or 3, and once in-app-only buttons such as Pinterest's are set aside, about **15 expose a permission or licence signal a server can verify before fetching** — overwhelmingly open-content repositories, podcasts and stock libraries rather than the social and video platforms that drive consumer demand. ## Platform contracts confine downloading to first-party buttons

None of the 18 social platforms reviewed grants third-party tools a general right to download other people's media, and the terms of at least 14 restrict automated access, scraping or copying. TikTok's US terms (15 July 2026, now issued by TikTok USDS Joint Venture LLC) bar automated extraction of any content without written approval (§3.4) and tie other users' licence to download to the poster's settings (§3.5) ([TikTok US Terms](https://www.tiktok.com/legal/page/us/terms-of-service/en)). Meta's terms ban automated collection on Instagram (§4.2) and Facebook (§3.2), logged in or not, and its developer guidance names instagram.com, facebook.com and Meta's GraphQL endpoints as off-limits to automated requests outside the Platform APIs ([Meta: Automated Data Collection](https://developers.facebook.com/documentation/development/terms-and-policies/automated-data-collection)); Facebook's help centre says others' reels and videos cannot be downloaded, while users can save their own reels from the mobile app now that every video became a reel in September 2025 ([Facebook Help](https://www.facebook.com/help/android-app/1005944300373812)). X's terms (9 October 2026) require access only through published interfaces, prohibit crawling and scraping without written consent, and set liquidated damages of **US$15,000 per million posts** for anyone who requests, views or accesses more than a million posts in 24 hours, with anyone who knowingly assists jointly liable ([X Terms, Open Terms Archive copy](https://raw.githubusercontent.com/OpenTermsArchive/pga-versions/main/X/Terms%20of%20Service.md)); X's own video download is a subscriber feature governed by an uploader toggle set at posting time that cannot be changed later ([X Help](https://help.x.com/en/using-x/x-videos)). Snap's terms (21 September 2026) are the clearest contractual no, forbidding copying, archiving or downloading except through the service's intended functionality ([Snap Terms](https://snap.com/en-US/terms)); Flickr forbids downloading anything not made available for download ([Flickr Terms](https://www.flickr.com/help/terms)); and Pinterest bans automated copying (§2(a)) even though its own *Download image* button works on any image Pin ([Pinterest Terms](https://policy.pinterest.com/en/terms-of-service)).

Sanctioned API routes are narrowing or becoming paid. Reddit's Responsible Builder Policy (November 2025) requires approval for all new API access and separate written approval for commercial use ([r/redditdev announcement, mirror](https://r.datuan.dev/r/redditdev/comments/1oug31u/introducing_the_responsible_builder_policy_new/)); X now sells API access by usage at **$0.005 per post read** with a three-million-read monthly cap ([X API pricing](https://docs.x.com/x-api/getting-started/pricing)); Google stopped issuing Tenor keys in January 2026 and shut the Tenor API on 30 June 2026 ([9to5Google](https://9to5google.com/2026/06/30/google-tenor-api-gif-updates/)); Tumblr's API agreement forbids caching beyond three days and requires honoring deletions within 24 hours ([Tumblr API agreement](https://www.tumblr.com/docs/en/api_agreement)); and Telegram's February 2026 content-licensing terms forbid scraping and aggregation beyond ordinary use ([Telegram content licensing terms](https://telegram.org/tos/content-licensing)). Silence is not a licence: Bluesky's terms and mastodon.social's current terms say nothing about scraping, but neither grants third parties any rights in users' content ([Bluesky Terms](https://bsky.social/about/support/tos); [mastodon.social terms](https://mastodon.social/api/v1/instance/terms_of_service)).

Video, audio and education platforms follow the same pattern. Dailymotion's July 2026 terms define the viewer licence as streaming-only and ban automated access and AI training ([Dailymotion Terms](https://legal.dailymotion.com/en/terms-of-use/)); Kick (March 2026), Rumble (September 2026), Bilibili (May 2025), Mixcloud and Coursera (January 2026) prohibit copying, scraping or automated retrieval ([Kick Terms](https://kick.com/terms-of-service); [Rumble Terms](https://rumble.com/s/terms); [Bilibili agreement, mirror](https://www.elawcn.com/agreement/2025/1120/1648.html); [Mixcloud Terms](https://www.mixcloud.com/terms/); [Coursera Terms](https://www.coursera.org/about/terms)). An open licence does not override the platform contract: TED talks are CC BY-NC-ND 4.0, yet TED expressly forbids scraping video from its site ([TED usage policy](https://www.ted.com/about/our-organization/our-policies-terms/ted-talks-usage-policy)). SoundCloud is the cautionary case for permission flags: its consumer product serves uploader-enabled downloads to signed-in listeners, but its API Terms (§05) forbid any file-save or offline feature in third-party apps even for those tracks ([SoundCloud API Terms](https://developers.soundcloud.com/docs/api/terms-of-use)). Spotify's Developer Terms bar facilitating stream ripping or permanent copies, and Apple's Media Services Terms (September 2026) allow access only through Apple's software ([Spotify Developer Terms](https://developer.spotify.com/terms); [Apple Media Services Terms](https://www.apple.com/legal/internet-services/itunes/us/terms.html)). A 2025–26 wave of revisions also added AI-training and data-mining bans at Dailymotion, Spotify, Apple, Coursera, Mixcloud and Bandcamp, so any pipeline that passes downloaded media to machine learning needs a separate gate ([Bandcamp Terms](https://bandcamp.com/terms_of_use)).

### YouTube's API licenses display and playback, never files

YouTube stacks three independent prohibitions, which is why holding a YouTube Data API key confers no right to download. The Terms of Service forbid downloading unless the Service expressly authorizes it or YouTube (and, where applicable, the rights holders) give prior written permission; forbid circumventing features that prevent or restrict copying; and forbid automated access other than by robots.txt-compliant search engines. The text varies by region — the US English render is dated 15 December 2023 and the French-region English render 9 January 2026 — so compliance records should store the version that applied to each user ([YouTube Terms, US](https://www.youtube.com/static?template=terms&hl=en&gl=US); [YouTube Terms, France](https://www.youtube.com/static?gl=FR&template=terms&hl=en)). The API Services Terms reserve all rights in the API services and data, grant **no right to reproduce or distribute audiovisual content**, state that such content is available only through the API services (§16.3), and limit the licence grant to displaying YouTube brand features (§10.1) ([YouTube API Services Terms](https://developers.google.com/youtube/terms/api-services-terms-of-service)). The Developer Policies then tell API clients not to "download, import, backup, cache, or store copies of YouTube audiovisual content" without prior written approval (III.E.1(a)) and not to offer offline playback (III.E.1(b)); they also ban scraping (III.E.6), separating audio from video (III.I.7), background playback (III.I.9) and retrieving API data, including audiovisual content, by any technology other than the API services (III.I.14) ([YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). The API therefore licenses metadata and playback inside YouTube's own embedded player. Pairing API metadata with stream extraction breaches III.E.1, III.I.14 and the Terms at the same time, and none of the policy revisions through June 2026 loosened these rules ([YouTube API revision history](https://developers.google.com/youtube/terms/revision-history)).

| Layer | Provision | Effect on a downloader |
|---|---|---|
| YouTube Terms of Service | Permissions and Restrictions, items 1–3 | No downloading unless the Service expressly allows it or YouTube grants written permission; no circumventing copy restrictions; no automated access |
| API Services Terms | §16.3, §10.1, §3.1 | No right to reproduce or distribute audiovisual content; licence limited to brand display and building API clients |
| Developer Policies | III.E.1(a)–(b) | No downloading, caching, storing or offline playback of audiovisual content |
| Developer Policies | III.E.6, III.I.7, III.I.9, III.I.14 | No scraping; no separating audio from video; no background play; no non-API retrieval |
| Developer Policies | III.E.4 | API data kept no longer than 30 days without refresh; deletion requests honored within 7 days |

Two consequences follow. A Creative Commons licence on a YouTube video is the creator's copyright permission, not YouTube's permission to acquire the file through YouTube ([YouTube Help: licence types](https://support.google.com/youtube/answer/2797468?hl=en)). And the only sanctioned routes are first-party: Studio download of one's own uploads at 720p or 360p, capped at five downloads per video per 24 hours; Google Takeout exports of one's own uploads in original format or MP4; and Premium offline copies that stay bound to the app and account for 29 days, or 48 hours in some regions ([YouTube Help: download your videos](https://support.google.com/youtube/answer/56100?hl=en); [YouTube Help: watch offline](https://support.google.com/youtube/answer/11977233?hl=en)). For a compliance-first product, the YouTube feature set is metadata and embedding through the official API and player plus deep links into those three routes.

## Two courts treat YouTube's cipher as a lock, and enforcement now reaches yt-dlp

### US exposure runs through §1201 while the Yout appeal waits

In the United States the decisive statute for a YouTube downloader is the DMCA's anti-circumvention provision, not ordinary infringement law. Section 1201 bans circumventing a measure that controls access to a work and separately bans trafficking in any technology, product or **service** that is primarily designed to circumvent, has only limited other commercially significant purpose, or is marketed for circumvention; the triennial exemptions excuse only the act and cannot be raised against trafficking claims, and circumvention is defined as acting without the copyright owner's authority ([17 U.S.C. §1201](https://www.law.cornell.edu/uscode/text/17/1201)). The major labels' amended complaint against Suno argues that fair use is no defense to anti-circumvention claims and seeks up to $2,500 per act ([Digital Music News](https://www.digitalmusicnews.com/2025/09/22/suno-lawsuit-amended-complaint-labels/)).

The case law is thin, and private and judicial actors have split. The RIAA's 2020 notice that took youtube-dl off GitHub alleged circumvention of YouTube's rolling cipher; GitHub reinstated the project on 16 November 2020 after the EFF argued that running YouTube's own player JavaScript is not circumvention and the maintainers removed unit tests that referenced commercial music videos, and GitHub then created a review process for §1201 claims and a $1 million developer defense fund ([GitHub blog](https://github.blog/2020-11-16-standing-up-for-developers-youtube-dl-is-back/); [EFF](https://www.eff.org/deeplinks/2020/11/github-reinstates-youtube-dl-after-riaas-abuse-dmca)). The only reasoned court ruling went the other way. In Yout v. RIAA, Judge Underhill of the District of Connecticut dismissed Yout's request for a declaration of non-circumvention on 30 September 2022, holding that YouTube's anti-download scheme is a technological measure that can be effective even though it can be circumvented, and that §512(f) misrepresentation claims do not reach §1201-based takedown notices ([CMU](https://completemusicupdate.com/stream-ripper-yout-circumvents-youtubes-technical-protection-measures-court-concludes/); [Eric Goldman](https://blog.ericgoldman.org/archives/2022/10/anti-circumvention-takedowns-arent-covered-by-512f-yout-v-riaa.htm)). The Second Circuit heard the appeal on 5 February 2024; one judge questioned deciding the issue without discovery, and RIAA counsel reportedly conceded that individual downloads may be exempt while mass downloading is not ([TorrentFreak, February 2024](https://torrentfreak.com/appeals-court-hears-riaa-and-yout-in-high-stakes-streamripper-case-240209/)). Briefing continued into late 2025, with Suno and Udio filing as amici and Yout arguing that YouTube has no access control at all, and both sides filed letters on the Supreme Court's Cox decision in March 2026; **no Second Circuit decision had been found as of 24 November 2026** ([TorrentFreak, November 2025](https://torrentfreak.com/yout-and-riaa-clash-in-court-over-youtubes-alleged-copyright-barriers/); [TorrentFreak, April 2026](https://torrentfreak.com/yout-com-hopes-supreme-courts-cox-ruling-helps-its-case-riaa-disagrees/)).

Kurbanov shows what losing looks like. The Fourth Circuit found US jurisdiction over the Russian operator of FLVTO and 2conv because the sites logged US visitors' IP addresses and sold geotargeted advertising through US brokers; after he abandoned the case and withheld evidence including server logs, the court entered a default judgment of **$82,922,500 for 1,618 works** (about $51,250 per work) and enjoined him from circumventing technological measures, and his appeal was dropped in August 2023 for lack of funds ([TorrentFreak, 2020](https://torrentfreak.com/appeals-court-revives-record-labels-lawsuit-against-youtube-rippers-200626/); [TorrentFreak, 2022](https://torrentfreak.com/?p=215056); [TorrentFreak, 2023](https://torrentfreak.com/youtube-rippers-run-out-of-money-give-up-on-83m-riaa-legal-battle-230810/)). The Supreme Court's Cox v. Sony decision of 25 March 2026 narrowed contributory liability to inducement or services tailored to infringement and credited Cox's warnings and terminations, which helps a general-purpose tool with real non-infringing uses ([Supreme Court docket](https://www.supremecourt.gov/docket/docketfiles/html/public/24-171.html); [Mayer Brown](https://www.mayerbrown.com/fr/insights/publications/2026/03/supreme-court-significantly-narrows-liability-for-contributory-copyright-infringement)). But the RIAA argues that §1201 liability stands independently of Cox, and Grokster still punishes marketing that promotes infringing uses ([Justia: MGM v. Grokster](https://supreme.justia.com/cases/federal/us/545/913/)). The §512 safe harbors — a designated agent costs $6 and lapses after three years — limit infringement liability, not circumvention liability ([Copyright Office FAQ](https://www.copyright.gov/dmca-directory/faq.html)). Platforms are litigating too: Reddit's October 2025 suit against Perplexity, SerpApi, Oxylabs and AWMProxy includes §1201 trafficking claims against scraping intermediaries ([Bloomberg](https://www.bloomberg.com/news/articles/2025-10-22/reddit-sues-perplexity-others-over-alleged-data-scraping)).

### Hamburg settled the cipher question, and blocking orders now spread by affidavit

Germany has decided the question at appellate level. On 21 November 2024 the Hamburg Higher Regional Court (OLG Hamburg, 5 U 54/23) upheld the labels' win against Uberspace, the host of the youtube-dl.org website. It held that the rolling cipher is an effective protection measure because an average user cannot easily bypass it, that the existence of other tools does not make it ineffective, that journalistic or archival uses are irrelevant when a tool is primarily used to circumvent, that users act in bad faith, and that a host serving a page that merely links to the tool is liable ([heise](https://heise.de/-10181247)). Further appeal was not allowed, and no Federal Court of Justice outcome has been found ([heise](https://heise.de/-10179284)). EU law points the same way: Article 6(2) of the InfoSoc Directive covers circumvention services, Article 6(4) refuses to let private copying override protection measures on on-demand services offered on contractual terms, ACI Adam (2014) excludes unlawful sources from private copying, and VCAST (2017) held that a commercial service making copies for users is judged on its own acts rather than borrowing their private-copying exception — directly relevant to any hosted downloader ([EUR-Lex: Directive 2001/29/EC](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32001L0029); [Kluwer: ACI Adam](https://legalblogs.wolterskluwer.com/copyright-blog/no-more-downloading-from-unlawful-sources/); [Kluwer: VCAST](https://legalblogs.wolterskluwer.com/copyright-blog/up-in-the-cloud-some-reflections-on-the-cjeu-judgment-in-vcast/)). Every hosting provider serving EU users must also run a Digital Services Act Article 16 notice-and-action mechanism ([Springlex: DSA Article 16](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-16/)).

Outside the US, rightsholders rarely need anti-circumvention law to close music-oriented rippers; ordinary infringement theories suffice — communication to the public and joint tortfeasance in the UK, a sole function of enabling unauthorized reproduction in Canada, prima facie infringement by rogue sites in India.

Targets are defined by purpose and use profile — music focus, anonymity, ignored takedowns, traffic — more than by the strength of any protection measure; Italy's anti-piracy federation puts stream ripping at about 30% of online music piracy, and the USTR's 2025 Notorious Markets review, released in March 2026, again lists Y2Mate and SaveFrom ([CMU, 2024](https://completemusicupdate.com/french-and-italian-record-industries-secure-new-web-blocks/); [USTR 2025 Notorious Markets List](https://ustr.gov/sites/default/files/files/Press/Releases/2026/2025%20Notorious%20Markets%20List%20%28final%29.pdf)). And pressure has moved upstream: IFPI's September 2026 submission asks that yt-dlp be listed alongside SaveFrom and two Y2mate sites, so a wrapper that ships yt-dlp with YouTube enabled inherits that exposure ([TorrentFreak, September 2026](https://torrentfreak.com/ifpi-wants-open-source-youtube-downloader-yt-dlp-on-eu-piracy-watch-list/)).

YouTube's own measures keep thickening, which strengthens the argument that they effectively control access. PO tokens produced by BotGuard, DroidGuard or iOSGuard attestation are now required for streaming URLs on most clients and are bound to video IDs, the web client serves only SABR formats, and tv-client formats are DRM-protected for requests without cookies ([yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)). No court has ruled on PO tokens, SABR or the 2025 JavaScript challenges, and no 2025–26 YouTube legal letters to downloader operators were found; earlier, YouTube ordered the Invidious front-end to shut down in 2023, and Free Download Manager dropped YouTube support after a Google complaint in 2021 ([TorrentFreak: Invidious](https://torrentfreak.com/youtube-orders-invidious-privacy-software-to-shut-down-in-7-days-230609/); [TorrentFreak: Free Download Manager](https://torrentfreak.com/free-download-manager-removes-youtube-support-after-google-complaint-211025/)).

### Operator practices cut infringement risk but cannot cure circumvention

Synthesizing the cases above gives a clear risk gradient for design choices; it is an interpretation of the evidence, not settled law.

| Design choice | Relative risk | Why |
|---|---|---|
| PO-token generation, BotGuard emulation, client spoofing | Very high | Built to defeat attestation; fits the statutory idea of bypassing a measure more squarely than the cipher does |
| Any DRM handling | Very high | Encryption is the classic protection measure under §1201 and Article 6 |
| Solving YouTube's signature and n-parameter challenges | High | Treated as circumvention by D. Conn. (2022) and OLG Hamburg (2024); US appeal pending |
| Cookie or session import; paywalled or private content | High | Defeats access controls and breaches terms |
| Music-focused "YouTube to MP3" product or branding | High | Primary target in at least eight jurisdictions |
| Ad-monetized public site with US-geotargeted ads | High | Kurbanov jurisdiction and statutory damages |
| Public multi-user hosted instance | Elevated | §1201 and Article 6 cover services; VCAST judges the operator's own acts |
| Private single-user self-hosting without circumvention | Lower | Fewer trafficking and public-offering signals |
| Owner exports, CC or public-domain direct files, honoring platform download flags | Low | Owner authority or licence, and no measure in the path |

None of the standard operator practices defeats a circumvention claim, which has to be handled by design, but they do reduce infringement and inducement exposure. The baseline is a registered and renewed DMCA agent; a notice-and-takedown and counter-notice flow that doubles as the DSA Article 16 mechanism; a repeat-infringer policy that is actually enforced, since Cox lost its safe harbor in BMG v. Cox for categorically ignoring one notice sender ([Justia: BMG v. Cox](https://law.justia.com/cases/federal/appellate-courts/ca4/16-1972/16-1972-2018-02-01.html)); blocklists that can absorb court-ordered mirror lists; GitHub-style technical and legal triage of circumvention complaints; terms and interface copy that discourage infringement; and test fixtures that use only the project's own or CC and public-domain media, because commercial-music fixtures were used against youtube-dl. Per-job ownership attestations are useful evidence against inducement but untested as a liability shield, and they cannot unlock circumvention features.

Privacy is where regulatory and litigation risk align. IP addresses are personal data under GDPR Recital 30 and the CJEU's Breyer ruling, hashed or pseudonymised IPs remain personal data under the EDPB's January 2025 guidelines, and Article 5 requires purpose limitation, minimisation and storage limitation ([GDPR Recital 30](https://gdpr-info.eu/recitals/no-30/); [Covington on Breyer](https://www.insideprivacy.com/international/cjeu-confirms-dynamic-ip-addresses-to-be-personal-data/); [EDPB](https://edpb.europa.eu/news/news/2025/edpb-adopts-pseudonymisation-guidelines-and-paves-way-improve-cooperation_en); [GDPR Article 5](https://gdpr-info.eu/art-5-gdpr/)). Kurbanov adds that kept logs become discovery targets. The defensible default is no IP logging, in-memory rate limiting with a short time-to-live or truncated addresses, no source URLs stored alongside user identifiers, aggregate metrics only and short documented retention — with the caveat, which counsel should confirm, that logs must be preserved once litigation is reasonably anticipated. No regulator guidance fixing a retention period for abuse-prevention logs was found.

## No competitor is clean, mobile-first and sustainably funded at once

The market splits into three groups, each failing differently. Paid desktop wrappers sell reliability and break together whenever YouTube changes. 4K Video Downloader Plus has a capped free Starter tier (ten downloads a day, per TidBITS), Lite at $15 a year and Personal and Pro lifetime licences at $25 and $45, and holds 4.6 stars from 13,406 Trustpilot reviews; its August 2026 release reworked subscription polling to reduce the risk of YouTube restricting users' IP addresses, yet a 20 November 2026 review reports YouTube failures and a 23 November company reply told a paying customer that the classic app had been discontinued and offered a discounted upgrade ([4K product page](https://www.4kdownload.com/products/videodownloader-42); [TidBITS](https://tidbits.com/watchlist/4k-video-downloader-plus-26-2/); [Trustpilot: 4K](https://www.trustpilot.com/review/www.4kdownload.com)). SnapDownloader, paid after a 48-hour trial, suffered a wave of error-code-3037 failures in August 2026, and one lifetime buyer reported it working about three-quarters of the time ([Trustpilot: SnapDownloader](https://www.trustpilot.com/review/snapdownloader.com)). VidJuice UniTube claims more than 10,000 sites, with lifetime prices quoted anywhere from $29.95 to $69.95 and complaints about a five-reinstall cap ([iTechGuides](https://www.itechguides.com/products/vidjuice-unitube/); [Trustpilot: VidJuice](https://www.trustpilot.com/review/vidjuice.com?page=2)). Video DownloadHelper pairs a no-tracking promise with a one-time licence, but its Chrome build excludes YouTube and users reported lifetime licences going inactive after a move to server-managed licensing ([Chrome Web Store](https://chromewebstore.google.com/detail/video-downloadhelper/lmjnegcaeklhafolokijcfjliaokphfk); [VDH user forum](https://groups.google.com/g/video-downloadhelper-q-and-a/c/UNm9ctxLIU0)).

The free open-source tools are clean but technical or narrow. yt-dlp, Parabolic (MIT), Open Video Downloader (AGPL-3.0), Stacher, Seal (GPL-3.0) and NewPipe carry no ads, but they are command-line or desktop programs, or Android apps distributed outside Google Play ([Parabolic](https://github.com/NickvisionApps/Parabolic); [Open Video Downloader](https://github.com/jely2002/youtube-dl-gui); [Seal on F-Droid](https://f-droid.org/packages/com.junkfood.seal/); [NewPipe](https://newpipe.net/)). Cobalt came closest to a polished, private web product — no ads or trackers, a zero-log policy, on-device remuxing that works on iOS 15+ and handles large files on iOS 18+, and clear errors for DRM-locked videos and rate limits — but YouTube became unavailable on its main instance in mid-2025 and the project is now dormant ([cobalt about page](https://cobalt.tools/about/general); [cobalt 11.0 changelog](https://github.com/imputnet/cobalt/blob/main/web/changelogs/11.0.md); [cobalt 11.2 changelog](https://github.com/imputnet/cobalt/blob/main/web/changelogs/11.2.md)). NewPipe users were stuck at 360p during YouTube's SABR rollout until a June release (v0.28.8) worked around it ([NewPipe releases](https://github.com/TeamNewPipe/NewPipe/releases)).

The ad-funded web rippers that dominate traffic are both the category's trust deficit and its enforcement target. SaveFrom and Y2Mate rely on push-notification permission traps, redirects and fake virus alerts; Malwarebytes tracks an adware family named after SaveFrom; and clones and lookalikes such as y2mate.lt and snapsave.io are flagged as malicious or phishing ([PCRisk](https://pcrisk.com/removal-guides/14858-savefrom-net-virus); [Malwarebytes: Adware.SaveFrom](https://www.malwarebytes.com/blog/detections/adware-savefrom); [MalwareTips: y2mate.lt](https://tools.malwaretips.com/url-scan/y2mate.lt); [Gridinsoft: snapsave.io](https://gridinsoft.com/online-virus-scanner/url/snapsave-io)). Downloader branding is also a favourite malware lure. The StealTok campaign (April 2026) planted at least 12 TikTok-downloader extensions with more than 130,000 users in Chrome and Edge, several with Featured badges, that turned malicious six to twelve months after publication; GhostPoster (January 2026) hid backdoors in about 34 extensions including YouTube and Instagram downloaders; and attackers swapped JDownloader's official installers for a Python remote-access trojan on 6–7 May 2026 ([Akamai](https://www.akamai.com/blog/security-research/stealtok-130k-users-compromised-by-data-stealing-tiktok-video-downloaders); [Malwarebytes: GhostPoster](https://www.malwarebytes.com/blog/news/2026/01/firefox-joins-chrome-and-edge-as-sleeper-extensions-spy-on-users); [Malwarebytes: JDownloader](https://www.malwarebytes.com/blog/news/2026/05/attackers-replaced-jdownloader-installer-downloads-with-malware)). Chrome's store policy already lets Google keep video downloaders out of featured placements ([Chrome Web Store policy](https://developer.chrome.google.cn/docs/webstore/program-policies/featured-products)).

Honesty about quality and failure is the other unowned gap. YouTube's best audio is roughly 160 kbps Opus, so 320 kbps MP3 options merely inflate files — a point even 4K's own blog concedes — while SnapSave advertises 4K downloads with sound but admits in its FAQ that rendering loses audio ([Appuals](https://appuals.com/why-converting-youtube-to-320kbps-mp3-is-a-waste-of-time); [4K blog](https://4kdownload.com/blog/2020/06/17/youtube-myth-debunked-320kbps-audio-streaming); [SnapSave](https://snapsave.app/)). Error messages mislead as well: on YouTube, yt-dlp's generic content-unavailable message actually signals a rate limit ([yt-dlp Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)).

Ranked by user impact, eight openings remain that no current product occupies together: a verifiably clean experience with no ads, redirects, notification prompts, installers or extensions; live per-platform status with an error taxonomy that names the cause and the next step; honest media labels with original, un-re-encoded output as the default; a share-sheet flow on both mobile platforms that needs neither sideloading nor copycat subscription apps (iOS users are currently sent to third-party file managers, and SnapTik-branded iOS apps charge weekly subscriptions); durable pricing that sells capacity and convenience rather than lifting artificial daily caps, backed by a written licence-continuity promise; mobile access to desktop-only power features such as subtitle and audio-track pickers and presets; verifiable privacy; and a compliance-first scope ([SnapSave](https://snapsave.app/); [App Store: SnapTik](https://apps.apple.com/us/app/snaptik/id1572161935)). The resulting position is a downloader one could recommend to both a parent and a legal team. Two caveats temper it: the most-demanded source, YouTube, is also the most fragile and the most legally exposed, and willingness to pay for a privacy-first web downloader is unmeasured — competitors anchor at $15–50 a year or $25–70 for a lifetime licence.

## The browser's own download manager beats every PWA API

The most reliable delivery path on every target browser is the oldest one: a same-origin link to an endpoint that streams the finished file with `Content-Disposition: attachment`, an ASCII `filename` plus an RFC 5987 `filename*`, the real `Content-Type`, `Content-Length`, `Accept-Ranges: bytes` and a strong validator, handing the transfer to the browser's own download manager ([MDN: Content-Disposition](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition)). The details bite. Chrome 65+ and Edge 79+ ignore the `download` attribute on cross-origin URLs, so the file endpoint must share the single-page app's origin or be proxied under it, and Firefox for Android honours `download` names only for `blob:` and `data:` URLs, so the filename must come from the header ([MDN browser-compat-data: a element](https://raw.githubusercontent.com/mdn/browser-compat-data/main/html/elements/a.json)). Safari does not decode percent-escapes in a plain `filename` and has mishandled very long names, so keep names short and ASCII-safe ([WebKit bug 249134](https://auto-bugs.webkit.org/show_bug.cgi?id=249134)). Never buffer media in JavaScript: Chromium on Android caps in-memory blobs at physical RAM divided by 100 and on-disk blobs at 6% of storage — about 20 MB in memory on a 2 GB phone — and the StreamSaver author recommends server-side `Content-Disposition` instead ([Chromium blob README](https://chromium.googlesource.com/chromium/src/+/main/storage/browser/blob/README.md); [StreamSaver.js](https://github.com/jimmywarting/StreamSaver.js)).

Resumption depends on validators that a default Express setup can get wrong. Chromium auto-resumes interrupted downloads with `If-Range` only when it holds a strong validator — an ETag, or a `Last-Modified` at least 60 seconds older than the response's `Date` — and otherwise declines to resume ([Chromium code review 1444253003](https://codereview.chromium.org/1444253003); [Chromium code review 1481143002](https://codereview.chromium.org/1481143002)). The `etag` package used across the Express ecosystem emits weak `W/` ETags from file stats by default, and a freshly prepared file's `Last-Modified` is under a minute old, so a download started right after preparation can present no strong validator at all; the fix is to disable the default ETag, set a strong one such as a content hash, and keep compression middleware away from media responses ([jshttp/etag](https://github.com/jshttp/etag)). Firefox for Android fixed pause-and-resume against servers that answer range requests with a full 200 only in version 154 ([Bugzilla 1819001](https://bugzilla.mozilla.org/show_bug.cgi?id=1819001)), while Chrome for Android has run downloads as a foreground service that survives backgrounding since 2017 ([Chromium code review 2735073002](https://codereview.chromium.org/2735073002)).

iOS is the weak spot. Safari saves downloads to Files › Downloads (iCloud Drive by default), not to Photos ([Apple Support](https://support.apple.com/102440)). Background continuation is undocumented: iOS 26.1 users report downloads cancelled on switching apps, while another user saw a 2 GB file finish under auto-lock ([Apple Community](https://discussions-jp-prz.apple.com/en/thread/256211824); [MacRumors forums](https://forums.macrumors.com/threads/downloading-files-continuously-in-the-background.2461737)). Worse, **WebKit bug 290847**, open since April 2025 with no workaround, strands Home Screen web apps on an *Open in…* screen whenever they download an attachment, recoverable only by force-quitting ([WebKit bug 290847](https://bugs.webkit.org/show_bug.cgi?id=290847)) — and since iOS 26 every site added to the Home Screen opens as a web app by default ([WebKit: Safari 26](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/)). Despite EU (iOS 17.4+) and Japanese (iOS 26.2+) rules allowing other engines, no browser maker had shipped a non-WebKit engine on iOS by June 2026, so every iOS browser should be treated as Safari ([MacRumors, June 2026](https://macrumors.com/2026/06/17/webkit-rule-costs-ios-users-browser-performance); [Apple: alternative engines in Japan](https://developer.apple.com/support/alternative-browser-engines-jp)).

PWA value splits by engine. Web Share Target, the manifest feature that lets a user share a link from the TikTok or Instagram app straight into the downloader, works in Chrome for Android 76+ but not in Safari, Firefox or Android WebView, and in practice requires an installed WebAPK, which only Chrome with Google Mobile Services and Samsung Internet on Samsung devices create ([browser-compat-data: share_target](https://raw.githubusercontent.com/mdn/browser-compat-data/main/manifests/webapp/share_target.json); [MDN: installable PWAs](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)). Background Fetch (Chromium 74+) lands responses in quota-bound Cache Storage and is worse than a native download for large media; Background Sync adds nothing when the server owns the job; and `showSaveFilePicker` reached Chrome for Android in version 132 without atomic writes and with awkward save-name handling, while WebKit opposes it and Firefox has a negative position ([browser-compat-data: Background Fetch](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/BackgroundFetchManager.json); [web-features: File System Access](https://web-platform-dx.github.io/web-features-explorer/features/file-system-access/); [blink-dev intent to ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/x3IcFv2jY6c)). On iOS, installing a web app brings Web Push (16.4+, requested from a user gesture), Declarative Web Push (18.4) and exemption from Safari's seven-day storage wipe — but installation is exactly where downloads break ([WebKit: Web Push for web apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/); [WebKit: Declarative Web Push](https://webkit.org/?p=16535); [WebKit: seven-day cap](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)).

Clipboard reading now works in every engine, but only from a user gesture and with three different experiences: Safari 13.1 and iOS 13.4 show a one-item Paste callout whose dismissal rejects the promise; Chrome 66+ asks for the `clipboard-read` permission; and Firefox 125+, on desktop and Android, shows a paste menu for content the page did not write ([browser-compat-data: Clipboard](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Clipboard.json); [WebKit: Async Clipboard API](https://webkit.org/blog/10855/async-clipboard-api/); [Bugzilla 1877400](https://bugzilla.mozilla.org/show_bug.cgi?id=1877400)). The robust pattern is a visible URL field plus a Paste button that calls `readText()` only inside its click handler, falls back on rejection to focusing the field with a long-press hint, and also listens for native `paste` events — served over HTTPS everywhere, because `navigator.clipboard` does not exist in insecure contexts. On Android, Share Target removes the paste step for installed users; on iOS, paste remains the main input path.

Live progress has to assume the page will be paused. Over HTTP/1.1, Server-Sent Events share a limit of six connections per browser and host across all tabs, which Chrome and Firefox have declined to lift, whereas HTTP/2 negotiates around 100 streams ([MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). Chrome throttles hidden-page timers to once a second and, after five minutes, to once a minute ([Chrome: timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)); Chrome for Android freezes background pages after five minutes ([blink-dev: freezing](https://groups.google.com/a/chromium.org/g/blink-dev/c/NKtuFxLsKgo)); and iOS suspends pages and drops sockets, with reports that EventSource's error event never fires on iOS 18 and that new WebSockets can hang after resume ([Apple Developer Forums](https://developer.apple.com/forums/thread/765183); [WebKit bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073)). The design that survives is server-owned job state with a REST snapshot; SSE over HTTP/2 with event IDs, retry hints, heartbeats and `Last-Event-ID` support; a client that reconnects and refetches the snapshot on `visibilitychange`, `pageshow`, `online` and `resume`; a watchdog of roughly 45 seconds; polling as a fallback; and no WebSocket.

Accessibility requirements are concrete under WCAG 2.2 (current edition 12 December 2024): targets of at least 24 by 24 CSS pixels (2.5.8), with 44 by 44 advisable for primary actions; focused controls never fully hidden by sticky bars or the on-screen keyboard (2.4.11); 4.5:1 text contrast and 3:1 contrast for progress bars and focus indicators (1.4.3, 1.4.11); progress and status announced without moving focus (4.1.3); and Timing Adjustable (2.2.1) for expiring download links unless the limit exceeds 20 hours ([W3C: WCAG 2.2](https://www.w3.org/TR/WCAG22/); [W3C: Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). Use a native `<progress>` element, which MDN recommends over the ARIA role, leave it indeterminate while a job is queued, announce only milestones through a single throttled polite status region, and reserve `role="alert"` for failures ([MDN: progressbar role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/progressbar_role)). Keeping prepared files for more than 20 hours satisfies 2.2.1 and supports resumption at the same time.

## A permission router, not an extractor, is the architecture that follows

The evidence converges on one principle: the sources that are technically fragile are the same ones that are contractually closed and legally exposed, while the permitted sources are stable, documented and often machine-checkable. That argues for building the product as a permission router with extraction engines behind it, rather than an extractor with a compliance layer bolted on. The decisions below are recommendations derived from the findings above, not findings in their own right.

| Decision | What to build | Evidence behind it |
|---|---|---|
| Make a versioned permission registry the core | Map each hostname, after alias normalization and redirect resolution, to a canonical platform, a category from 1 to 5, a permitted engine or API connector and the signal to check; seed the deny-list from yt-dlp's DRM and liability refusers plus Netflix, Apple Music, TIDAL and max.com; add a stricter DE/EU overlay; derive health from canary checks | Strict extractor patterns; unreliable *working* flag; the final Hamburg ruling |
| Keep YouTube extraction off by design | Exclude YouTube extractors from `--ies`; offer metadata and the embedded player through the official API, deep links to Studio download, Takeout and Premium, and a plain explanation | YouTube Terms; API §16.3; Policies III.E.1 and III.I.14; Yout and OLG Hamburg; IFPI nomination |
| Ship no JavaScript runtime in the hosted service | Pass `--no-js-runtimes` and `--no-remote-components`; any self-hosted exception uses Deno only, pinned together with yt-dlp-ejs | The runtime exists to solve the cipher; Deno runs with zero grants while Node is described as insecure |
| Prohibit evasion in code and in the image | Build argv from an allowlist; reject impersonation, cookies, PO-token arguments, `--xff` other than `never`, `--allow-unplayable-formats`, `--exec`, `--netrc-cmd` and `--write-*link`; leave curl_cffi, PO-token plugins, mp4decrypt, N_m3u8DL-RE and aria2 out of the image | 21 extractors auto-use curl_cffi; risk gradient; aria2 CVEs |
| Treat DRM as a hard stop | Run a `-J` metadata preview; refuse on `_has_drm` or a DRM error with an explicit message; never decrypt | yt-dlp's DRM handling; Widevine gap in HLS detection |

Cox, Grokster, Kurbanov, the youtube-dl takedown |

| Compete on honesty, not site counts | Live per-platform status; an error taxonomy that names rate limits, login walls, DRM refusals, region locks, platform refusals and source changes; labels for source codec, bitrate, resolution and language, with sizes from `filesize`, then `filesize_approx`, then bitrate times duration marked as estimates; no lossy upscales; a written licence-continuity promise | Competitor failure modes; yt-dlp size fields |

The YouTube decision deserves its steelman. GitHub and the EFF maintain that running YouTube's own JavaScript is not circumvention, the RIAA reportedly conceded at argument that individual downloads may be exempt, Cox has narrowed secondary liability, and the Second Circuit could still side with Yout. But a Yout win would remove only the US anti-circumvention layer; YouTube's Terms and API policies, the final Hamburg ruling and IFPI's targeting of yt-dlp would all stand. If the business nonetheless decides to offer YouTube, the least-exposed configuration is an off-by-default setting limited to self-hosted single-user installs, Deno with zero grants, yt-dlp and yt-dlp-ejs pinned together with remote components disabled, and no PO tokens, cookies or impersonation — accepting fewer formats, frequent breakage, a breach of YouTube's terms in every jurisdiction and high circumvention risk in Germany.

A baseline invocation for the permitted-source path, assembled from documented flag semantics and untested end to end because no downloads were run during this research, looks like this, with `YTDLP_NO_PLUGINS=1` and per-job `HOME` and `XDG_*` directories set in the environment ([local yt-dlp --help](file:///C:/Users/weeam%20server/Documents/download-link/.venv/Scripts/yt-dlp.exe); [local FFmpeg 9.0.2 options](file:///C:/Users/weeam%20server/AppData/Local/Microsoft/WinGet/Packages/BtbN.FFmpeg.GPL.9.0_Microsoft.Winget.Source_8wekyb3d8bbwe/ffmpeg-n9.0.2-39-g7adfbe40dc-win64-gpl-9.0/bin/ffmpeg.exe)):

```text
yt-dlp --ignore-config --no-plugin-dirs --no-js-runtimes --no-remote-components \
  --ies "<reviewed-allowlist>,-generic" --xff never --no-cookies \
  --proxy <egress-proxy> --socket-timeout 30 --downloader native \
  --cache-dir /work/<job>/cache -P home:/work/<job>/out -P temp:/work/<job>/tmp \
  -o "%(id)s.%(ext)s" --no-playlist --max-filesize <cap> \
  --newline --progress --progress-delta 1 --progress-template "download:%(progress)j" \
  --print "after_move:filepath" <url>

ffmpeg -nostdin -hide_banner -xerror -protocol_whitelist file \
  -max_alloc <bytes> -probesize <bytes> -analyzeduration <microseconds> \
  -i <local-input> -c copy -fs <cap> -t <cap> -progress pipe:1 -nostats <output>
```

Several open questions should shape the roadmap without blocking it. Whether a URL-fetching downloader is a DSA hosting service, whether per-job attestations reduce operator liability, and whether a Creative Commons licence supplies the copyright owner's authority that defeats a circumvention claim are all untested. Apple documents neither Safari's background-download nor its resume behaviour, and WebKit 290847 could be fixed silently, so each iOS release needs a device test covering a download over 1 GB, a mid-transfer network drop, five minutes in the background and a resume. Operationally, watch yt-dlp and gallery-dl weekly and FFmpeg and Streamlink monthly, re-run the extractor count at each yt-dlp upgrade, and route extractor updates through registry review rather than auto-updating code that bears on circumvention.

## Conclusion

The research changes the question a downloader has to answer. For a decade the category competed on whether a file could be extracted; in 2026 the extractor is a shared commodity — many rival tools wrap the same yt-dlp upstream that IFPI now names — and the scarce asset is knowing who granted permission and whether a machine can read the grant. Because the platforms that now work only with cookies, browser impersonation or attestation tokens are exactly the ones whose terms already forbid third-party downloading, refusing that tooling costs a compliance-first product almost no permitted coverage; it costs only the appearance of coverage. The routes that stay durable are the ones platforms control and keep investing in — owner exports, native download buttons, open licences and RSS enclosures — while third-party API access keeps narrowing.

The second implication is that compliance and product quality pull in the same direction. A registry that knows a source's category also knows what to tell users when a download is refused, turning the category's worst experience, silent breakage behind opaque error codes, into its clearest differentiator; the discipline that keeps IP addresses out of logs also shrinks discovery exposure; and the web primitive that makes phone downloads reliable — a plain attachment response with a strong validator — needs no extension or installer, the channels malware campaigns have repeatedly abused. Leaving YouTube out is robust to the pending Second Circuit ruling, so the risk worth watching is commercial rather than legal: whether users will pay for a downloader whose honesty extends to telling them what it will not do.
